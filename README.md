# dsh-desktop

A minimal Electron shell that wraps the DeepSeek Harness (DSH) web GUI as a
macOS desktop application. The harness itself is **not** modified: `dsh web`
runs as a sidecar Node process and this shell hosts its browser UI.

## Why sidecar (not embedding)

DSH ships native modules per platform (`sharp`, `node-pty`, `koffi`,
`@vscode/ripgrep`, sandbox backends). Running the harness in its own Node
process keeps those on the normal Node ABI — no `electron-rebuild` needed.

## How it works

1. Electron requests a single-instance lock.
2. It picks a free localhost port, then spawns `dsh web --port <port>`.
3. It polls `http://127.0.0.1:<port>/` until the server answers.
4. A `BrowserWindow` loads that URL (the same UI you see in a browser).
5. On quit / window-close it sends `SIGTERM` to the sidecar (then `SIGKILL`
   after 3s) so no orphan server is left behind.

### Sidecar resolution order

| Priority | Source |
|---|---|
| 1 | `DSH_BIN` env — explicit path/command |
| 2 | local `@deepseek-ai/dsh` — entry resolved from its `package.json` `bin` |
| 3 | `node_modules/.bin/dsh` — local bin shim |
| 4 | `dsh` on `PATH` |

## Run

```sh
npm start            # launch the window
DSH_SMOKE=1 electron .   # headless-ish smoke test: print SMOKE_OK and quit
```

Useful env overrides:

| Var | Effect |
|---|---|
| `DSH_BIN` | explicit `dsh` entry path/command |
| `DSH_NODE` | node binary used to run the bundled `bin.js` |
| `DSH_PORT` | fixed port instead of auto-pick |
| `DSH_HOST` | bind host (default `127.0.0.1`) |
| `DSH_CWD` | workspace root passed to the harness (default: your home) |
| `DSH_HOME` | harness data home (default `~/.dsh`) |
| `DSH_UPDATE_CHECK` | `0`/`false` disables the harness update check |
| `DSH_NPM_REGISTRY` | registry queried for the latest `@deepseek-ai/dsh` (default `https://registry.npmjs.org/`) |
| `DSH_UPDATE_URL` | page opened on "前往下载" (default the npm package page) |

## Harness update check

On launch the shell reads the bundled `@deepseek-ai/dsh` version, asks the npm
registry for the `latest` dist-tag, and — if the bundled version is older —
shows a dialog: **当前版本 / 最新版本**, with a **前往下载** button that opens
`DSH_UPDATE_URL`.

- Non-blocking and **silent on failure**: any network error/timeout is logged
  and ignored, never blocks or crashes the app.
- Disabled entirely with `DSH_UPDATE_CHECK=0` (useful for smoke tests/CI).
- Point `DSH_NPM_REGISTRY` at a mirror (e.g. `https://registry.npmmirror.com/`)
  if the default registry is slow or blocked.

## Build

```sh
npm run make-icon     # regenerate build/icon.icns from the DeepSeek whale favicon
npm run build         # electron-builder --mac  (targets: dir + zip)
npm run build:dir     # unpacked .app only (faster)
```

Outputs:
- `dist/mac-arm64/DeepSeek Harness.app` (unpacked)
- `dist/DeepSeek Harness-<version>-arm64-mac.zip` (distributable archive)

The build reuses `node_modules/electron/dist` via `electronDist` (no
re-download) and disables `@electron/rebuild` (`npmRebuild: false`) because the
harness runs under the bundled Node, not Electron. Signing/notarization is
documented in [`SIGNING.md`](SIGNING.md).

> **Peer-dependency gotcha (important when upgrading `@deepseek-ai/dsh`):**
> the harness declares several "abstract seam" packages (e.g. `dsh-fs`,
> `dsh-shell`, `dsh-sandbox`, `cordis-plugin-group`, …) as `peerDependencies`
> rather than `dependencies`, so electron-builder's production-only pruning
> drops them and the packaged sidecar dies with `ERR_MODULE_NOT_FOUND`. They are
> therefore pinned as **direct `dependencies`** in `package.json`. After any
> `@deepseek-ai/dsh` upgrade, re-run the completeness check and add any newly
> missing packages the same way:
>
> ```sh
> APP="dist/mac-arm64/DeepSeek Harness.app/Contents/Resources/app/node_modules"
> comm -23 <(ls node_modules/@deepseek-ai | sort) <(ls "$APP/@deepseek-ai" | sort)
> # ↑ empty = complete; non-empty entries must be added to `dependencies`
> ```

## Dev note: running from inside the DSH harness sandbox

If you launch this shell from *within* another sandbox (e.g. an agent running
under the harness's own `workspace-write` file sandbox), Chromium needs two
test-only workarounds — it cannot write to `~/Library/Application Support` nor
initialize its nested macOS sandbox from inside the outer sandbox:

```sh
# 1. @electron/get caches its ZIP here by default (blocked inside the sandbox):
export electron_config_cache="$PWD/.electron-cache"

# 2. run Chromium without its own sandbox, and put user data in the workspace:
node_modules/.bin/electron --no-sandbox --user-data-dir="$PWD/.electron-user-data" .
```

Running `npm start` normally on your own Mac needs **none** of this.
